# Firecrawl → MAD4B Control Plane (Woo Lab first consumer)

## Scope
This integration adds two **private WordPress Abilities** to the shared MAD4B Control Plane on a single consumer site: `mad4b/research-firecrawl-status` and `mad4b/research-firecrawl-preview`. Woo Lab is the first runtime consumer; other sites remain unconnected. Only authenticated `manage_options` users satisfying MAD4B_SCP_Policy::can_read can execute either ability. The abilities do not persist scraped content or mutate WordPress.

## Security
- Firecrawl remains internal-only, through the `mad4b-firecrawl-production_consumers` Docker network and its existing Basic Auth gateway, not the raw API.
- The hostname `gateway` and port 8080 are constant, not caller-supplied.
- Only HTTPS targets on an exact owner-configured allowlist are allowed, initially **example.com only**. Configure `MAD4B_FIRECRAWL_ALLOWED_HOSTS` in the consuming site's wp-config to expand the list; never wildcard unknown customer sites. SSRF controls also apply in upstream Firecrawl.
- Credential path: `/run/mad4b-local-vault/firecrawl-control-plane/consumer.credential` (owner www-data, 0600, directory 0700). File must contain exactly `username=...` and `password=...`, generated by the Firecrawl `manage-consumer.py` and securely provided on the VPS without outputting its contents. Do not commit, store in DB/options, expose through REST, or log it.
- No environment-type lock: absent credentials and network imply fail-closed. This is not gated by `local` or `staging`; the same code can serve future governed consumers after explicit configuration.
- Preview receives at most 256 KiB and returns at most 6000 characters; fails closed on any provider response other than HTTP 200 / success true.
- No automatic scheduling, site crawl, arbitrary URL proxying, or per-tenant permissions enabled. Dedicated Research Gateway with scoped grants and quotas remains a later step.

## Deployment
1. Land GitHub PR; verify PHP syntax + bridge unit test on Woo Lab PHP 8.5.
2. Install only the new MU plugin `wp-content/mu-plugins/mad4b-research-firecrawl.php` on Woo Lab; **never overwrite the entire existing Control Plane plugin**, which can have a different current release.
3. Generate `mad4b-woo-lab-control-plane` account with Firecrawl's owner-only helper. Deliver the credential into the Woo Lab private vault, mode 0600 and owner www-data. Maintain one identity per approved site.
4. Add `mad4b-firecrawl-production_consumers` to the existing Woo Lab PHP Compose service networks, using the recorded per-host stack override/manifest. Do not attach Nginx, DB, or any other site. Recreate only Woo Lab PHP service from its verified Compose definition, and test that existing traffic is healthy.
5. Using authenticated admin execution, inspect `mad4b/research-firecrawl-status` and run `mad4b/research-firecrawl-preview` with `https://example.com`. Verify denial to other hosts and anonymous requests. Never use public admin credentials for smoke tests.
6. Rollback: detach only Woo Lab PHP service from consumers network and remove its credential file and MU plugin, preserving Control Plane and Firecrawl services. Revoke `mad4b-woo-lab-control-plane` in the Firecrawl credential manager. No database, customer media or production site edits required.

The Compose runtime stack is managed separately on the VPS at `/opt/hostinger-migrations/hosting-3/etg-woocommerce-lab/stack/compose.yml`, not inside this WordPress repository; source-to-runtime parity of the network change needs an explicit versioned overlay/reconciliation.

## Local Sandbox transport admission

Woo Lab's existing `000-sandbox-guard.php` correctly rejects private Docker HTTP requests. The additional `mad4b-research-firecrawl-transport-exception.php` plugin runs **after** this local guard and clears **only** its exact `etg_sandbox_network_blocked` error for an in-flight, authorized Control Plane Firecrawl request scoped to fixed `gateway:8080` health GET or preview POST. It never lifts a different policy error or admits a caller-specified private URL; the original sandbox guard remains unchanged. Both MU plugins must be installed together. Run negative tests for unapproved host, non-admin user and direct ordinary WordPress HTTP calls.
