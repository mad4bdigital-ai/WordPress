Use for WordPress WP Users / Roles / Capabilities discovery, user-role mapping, audit of access to commerce/inquiries/quotes/bookings, site migrations and cross-company operator assignments. This Skill is non-authorizing guidance. Its site-neutral reference contract is `config/user-role-governance-contract.json`; that configuration is a policy blueprint, not a runtime role enforcer or provider certificate.

## 1. Resolve the identity and authority domains
1. Resolve exact enrolled Site Profile, site UUID, network/blog ID (when multisite), environment, current build and authenticated actor. Reject ambiguity between local lab, Staging and Production; never infer that matching hostnames, copied user IDs or database snapshots share identity.
2. Keep **WordPress WP_User roles/capabilities**, **MAD4B OAuth user-to-subject mapping**, and **MAD4B NHI grants / one-time approvals** distinct. Successful OAuth identity mapping is not a role grant. `current_user_can()` is not a substitute for the MAD4B provider, approval and exact-plan gates.
3. Discover available certified *read-only* role/capability inventory first. If missing, return `wordpress_role_inventory_read_unavailable`, and specify the bounded adapter needed. Do not substitute Raw SQL, user-list endpoints or host shell access for an absent certified capability.

## 2. Role discovery and effective-capability matrix
4. Inspect role definitions through a site-authorized WP role inventory (WordPress `wp_roles()` / `get_role()` semantics) and, only when explicitly authorized, effective user permissions through `WP_User`, `user_can()`, `current_user_can()` and context-specific `map_meta_cap()` outcomes. Cover site/blog scope, network super admins and plugins that filter capabilities; never equate the role label with proven authority.
5. Record capability provenance (core, plugin, site policy, explicit user grant, super admin, filtered/meta-cap) and compare desired vs observed permissions. Show an anonymized matrix keyed by capability and operational persona, not user names, emails, phone numbers or password/reset material.
6. Treat these as distinct *personas*, not assumed built-in role slugs: traveler/customer, inquiry reviewer/operator, commercial manager, booking/supplier operator, site administrator and developer/support. Resolve actual role slug and assignment only from the enrolled site. Support tenant-specific additional roles without hardcoding tourism-specific names.

## 3. Workflow gates and assignments
7. Build the separation-of-duties matrix for inquiry reception, qualification, nonbinding quote draft, final price approval, traveler acceptance, order/payment authorization, supplier booking and fulfillment. `accepted_for_processing` is NOT final quote approval; a read-only quote preview is NOT a sale; a notified traveler is NOT an accepting traveler.
8. For each transition, inspect both the effective WordPress capability and separately certified MAD4B ability/NHI approval. Rejection, managerial quote approval, Woo financial write and supplier booking must not inherit generic `edit_posts`, `manage_options`, `manage_woocommerce` or "operator" role access by implication. Missing entitlement means deny/PLAN_ONLY.
9. Inspect existing request-to-task/user assignments from the owning Commerce Composition / FluentBoards provider using certified read tools, exact site scope and non-PII identifiers. Detect unassigned jobs, disabled/deleted assignees, cross-company attribution, missing coverage, and impossible same-person approval duties. Do not assign or reassign a task without its exact provider-owned capability.
10. On multisite or multiple independent company installations, enumerate effective per-blog memberships and network super-admin overrides separately; never copy a site's capabilities, user ID, approval receipt or service-account credential to a different tenant. Each Site Profile owns its own role-to-persona mapping.

## 4. Least privilege, change governance and evidence
11. Flag excess `edit_posts` for customer roles, `edit_users` or `promote_users` for routine operators, inappropriate `manage_options` or `manage_woocommerce`, direct meta-cap overrides, unreviewed super-admin status, and unbound service accounts as **findings**. Evaluate plugin dependencies and existing grants; do not automatically remove privileges or disable an account on discovery alone.
12. Prepare an immutable change plan with before/after capability matrix, user/role/site fingerprints, actor, affected plugins, compatibility checks, lockout prevention, an unaffected administrator recovery route, backup/restore, rollback and exact readback. Reuse MAD4B's canonical plan/approval process; never authorize changes from the Skill or from a supplied JSON policy.
13. A role edit, user enrollment, deprovision, permission grant/revoke, or task assignment requires the *specific* certified, bounded, reversible provider ability, exact NHI grant, independent human approval when applicable, fresh target fingerprint, idempotency and audit. If the provider action is unavailable/unmounted, remain `PLAN_ONLY`. Never call `add_role`, `remove_role`, `WP_Roles::add_cap`, `WP_User::set_role`, or write `wp_usermeta` directly from this Skill.
14. Verify positive and negative access cases: customer cannot edit content/admin data; reviewer can see assigned inbox but not commercially approve; manager can approve only the exact authorized quote; booking operator cannot create an unapproved sale; unauthenticated guests are denied; existing administrator recovery remains possible. Test both WordPress native routes and provider endpoints, plus OAuth subject binding and multisite isolation where relevant.
15. Report an evidence-bound `role_inventory_status`, site-scoped persona/capability matrix, separation-of-duties violations, provider abilities and blockers, assignment anomalies, reversible plan and independent **PASS / BLOCKED / NOT_TESTED** results. Redact user-entered and personal data. Never claim site deployment, Production readiness or write capability from source-level Skills tests.
