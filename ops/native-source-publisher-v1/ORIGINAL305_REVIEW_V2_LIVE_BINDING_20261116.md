# Original305 — fix superseded review binding and preserve original approval authority

**Issue:** V1 historical incident-review request was bound to Supervisor V6 (`be76...`) even after original first-party CAS advanced the existing service to Supervisor V7 (`dd669...`). The request could not authorize a review of the current original service, and trying to accept the obsolete request would confuse old and new deployment identities.

**Permanent source correction:** `original305_incident_signed_review_v2.py --plan` validates the exact installed Registry V8 index, current root-owned HOLD evidence, Supervisor V7 source bytes and the current original systemd service unit (its SHA and exact `ExecStart` matching the same Supervisor). The V2 request includes service unit SHA; the V2 Ed25519 Master verification binds every one of those fields to one short-lived request. V1 signed approvals cannot satisfy V2. Any deployed code or unit changes must create a new request. Tests use only synthetic Ed25519 keys.

**Critical governance boundary:** The existing WordPress class `MAD4B_SCP_Approval_Tickets` is present in Central and has original `create_pending`, `decide_pending`, `validate_exact` actions. Its own code checks authenticated planning and approving identities and original ticket exact binding. Neither the `mad4b/original305-incident-review` WordPress approval workflow nor an original approved ticket for this incident has been enrolled. This file does not issue a ticket, impersonate a Master user, create a signed approval, delete/rename `HOLD`, or enable the timer; a signature-only check still explicitly says `original_wordpress_ticket_admission_verified=false`.

**Outstanding first-party operation:** Register the dedicated review ability and approved ticket-admission validator in the native WordPress control plane through its original governed release process. Have an authenticated Master admin issue/approve a ticket bound to the V2 exact incident request and let the actual Master signer issue the independent Ed25519 envelope. Only a separately authorized governed finalizer may close the historical HOLD with CAS, a durable audit/rollback receipt and no Host release Grant. A previous ad hoc direct marker-removal command was explicitly blocked by upstream execution safety checks; do not reroute or rephrase that blocked operation. Once the original authority closes the incident, activate the **same** readiness timer and independently verify at least two completed signed WordPress renewals while keeping `host_release_authorized=false`.
