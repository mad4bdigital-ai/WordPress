# Native Source Publisher v1 — Activation Gates

Status: HOLD. Not deployed.

## Reuse and separation

Native source release reuses verified Company Code Release CAS and backup engine,
existing Central exact-approval tickets, the same original 306/312/313 worker
contract and independently signed receipt flow. This is independent of remote
Hostinger 318 Host Authority, because the site is a local Docker-backed source.

## Missing capabilities, in order

1. Have the certified MAD4B publisher enroll an exact local Tours.dev target
   using a separate root-owned native source policy. The disabled template
   contains no real keys and MUST NOT be installed as an enabled policy.
2. Register the native publisher ability mad4b/native-source-release on
   the Central governed write surface. Approval Plan can then create an exact
   pending ticket tied to Git plan fingerprint, Site UUID, origin, and the
   source file preimage. Master Admin decides via the existing approval console.
   No auto-approval.
3. The trusted Central approval issuer must re-read that ticket and sign the
   plan-and-ticket-payload attestation with its separately enrolled key. The
   executor re-reads the live approved ticket immediately before any write,
   denying revocation, expiry, payload and site/profile drift.
4. A first-party Broker issuer separately signs a plan/job-bound release
   grant. Neither this source repo nor WordPress is a Broker private signer.
5. Through approved first-party enrollment, place the SHA-pinned handler,
   verifier, source dependency, evidence schema, immutable plan, approved
   grant and attestation in the root-private registry and stores. Register
   source.code.release in original 306 worker and original 313 independent
   verifier/finalizer. This MUST be a native approved install, not direct
   source-to-live copying.
6. Execute the original claimed Job only once. Handler verifies protected
   reservation, fresh original312, actual Central ticket, independent Master
   signature, Broker signature, exact Git blob and live CAS fingerprint.
   Backend provides atomic write, durable backup, JS syntax check and
   WordPress boot/readback; failed validation rolls back.
7. Independent original313 finalizer must sign the resulting exact readback.
   Then execute current browser regression (visible Apply on desktop/mobile,
   AJAX Clear, WPML, currency, Form 6) without response interception and
   rerun archive/JetSearch/Query310 post__in fail-closed acceptance.
