# MAD4B Unified Media Apply v1 — signed router

`mad4b.media.apply.v1` is the single typed interface for media mutations and preflight across registered WordPress public post types and public taxonomies. The signed Host Agent opcode is `media_apply`, dispatched through the existing Ed25519 trust, exact tenant binding, body hash, freshness, nonce anti-replay, and WordPress execution context. This does not register a generic shell, arbitrary SQL, or a generic attachment write capability.

Exact envelope `body`: `{ "contract":"mad4b.media.apply.v1", "target":{"kind":"post|term", "type":"registered-type", "id":123}, "adapter":"registered-adapter", "action":"preflight|apply|revoke", "payload": { ...adapter-specific exact schema... } }`.

Built-in typed adapters: `tour_association` delegates to the existing governed tour media association on signed `apply`/`revoke`; `term_featured_image` delegates read-only licensed asset verification, and requires a separately verified **human-approved** review and a signed executor before any mutation; `post_featured_image`, `post_registered_image`, and `term_registered_image` validate same-site existing image attachments, SHA256, registered image fields and CAS preimage hashes. These last three are **read-only preflight until the image review dispatcher is approved**, not active publishers. For JetEngine custom image fields the company adapter must register exact field names through `mad4b/media/apply/fields`; text/price/other meta fields never qualify automatically. A new adapter cannot become an arbitrary callback from an untrusted request.

The host PHP bridge supports `media_apply` alongside existing legacy `media_associate` for backwards compatibility. Legacy code is not removed until coverage and rollback tests establish parity. Existing registered backend grants and `human_only` policy remain intact: a fresh host signature authenticates transport but is NOT an editorial image approval.

Verified against Wayfatours Production: signed Esna taxonomy `preflight` returned `preflight_valid_approval_pending`, signed existing tour featured-image `preflight` returned `existing_attachment_preflight_valid`, and a signed attempted Esna `apply` was rejected with `mad4b_unified_media_term_signed_approval_executor_pending` and left meta unchanged. Direct security regression checks passed for cross-tenant, wrong post type, unregistered field, unknown adapter, stale preimage, mismatching attachment SHA and unapproved write.

The remaining gap is an authorized, reviewed `apply` implementation for **licensed term and generic custom field images** using an actual approved content asset from the existing workflow, atomic rollback and site-local attribution/translation verification. No signed receipt of those content writes exists yet. Do not mark Esna or the term-media writer complete.

## Signed AI image review + actual licensed term image application (2026-11-10)

Wayfatours Production `Review Policy` was explicitly changed to `ai_only` using the existing host-signed `policy` operation and read back successfully. This does not set `automatic_approvals=true`, and there is no general permission to publish content. The exact enrolled agent must remain enabled, have the matching grant, and match the site UUID and environment.

`term_featured_image` now supports a signed `review` action requiring the exact approved JPEG checksum, term pre-image, subject description, geographic evidence, and license facts. The asset-bound review record is audited and expires after 24h. A signed `apply` requires the *same* exact asset, ready AI policy, approved record, pinned tenant and pre-image. It creates a WordPress attachment using WP-CLI's real native media APIs, writes the taxonomy term's existing `featured_image` field to its local URL, maintains licensed attribution, and issues a signed-host readback receipt. On failure it restores term media and prior credits and deletes newly created attachment files. An independent repeat `apply` is rejected on changed pre-image and consumes the approval record on success. No arbitrary SQL or generic meta-write path is exposed.

Verified live on Wayfatours Esna term 2402, approval SHA `7ef8a0ce40b79847e13bcfd4ac603c7d7d817806d2a1c658523161c16508ef64`, attachment 69804, readback receipt SHA `160199199603a35ace0472293fefc2493ce9f1a524f638d11cb9d0613fc58cf7`. Chromium confirmed that EN and ES pages serve an actual 2560×1562 JPEG as their Elementor background, both render Marc Ryckaert + CC BY-SA 4.0 credits, both have 200 responses and zero JS uncaught errors. WordPress Media Readiness returned `media_ready=true` and the prior Esna P2 media alert changed to `resolved`. The demonstration does **not** certify all custom post-field writers; those remain preflight-only until their typed, reviewed mutation implementations are separately tested. Source Tours.dev has the router but not this Wayfatours-specific signed bridge and is not claimed to have executed Esna.

## Registered WordPress + JetEngine image writes — 2026-11-10

The common `media_apply` signed route now implements `review` and `apply` for `post_featured_image`, `post_registered_image`, and `term_registered_image`, in addition to the prior `term_featured_image`. Exact local attachment ID, SHA256, site identity, target kind/type/ID, registered image field, and compare-and-swap value hash are required. The signed AI reviewer creates a 24h, exact-object approval; the write consumes it once. The authorization is scoped to the *particular* field and attachment. Field values follow the genuine storage contract: WordPress Featured Image stores an attachment ID; JetEngine scalar `media` fields store a URL or ID according to the declared `value_format`. JetEngine media fields are enumerated from the actual registered meta schema (`get_meta_fields_for_object`), not guessed from names. Generic text/commerce fields, Galleries and Repeaters are intentionally not written by this scalar adapter; those require their own typed field adapters.

A live **unpublished** Wayfatours QA tour draft (69819) was used to verify two **actual changed writes** via host-signed WP-CLI: `_thumbnail_id` assigned the local licensed image attachment 69804 as numeric ID, and `image_vertical` received its local URL. Both returned `applied_verified` signed-host receipts and exact readback. A repeated signed write with the stale pre-image was rejected. The temporary draft was then deleted permanently; original Esna term 2402 and licensed image attachment 69804 were preserved. A separate signed `term_registered_image` QA on the existing Esna `featured_image` field verified the scalar URL format and one-time approval consumption without changing its correct existing image. No published tour image was changed.

On failure, the new local-image apply path restores the original field and invalidates the relevant WordPress post/term cache; a consumed approval is not reusable. WPML translated media values are not blindly overwritten; each target must carry its own correct pre-image and be explicitly reviewed. Existing signed term-media family behavior remains separate. No blanket `Purge All` is used. This is a host-applied, tested rollout on Wayfatours, not an Original 313 certification or an assertion of remote-company rollout.
