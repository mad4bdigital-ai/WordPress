# MAD4B VPS CPU: stale browser container + managed browser `docker exec` leakage

**Root cause verified on 14 Nov 2026 UTC / 15 Nov EET:** 8-vCPU Hostinger VPS had 62 running containers using `mad4b-firecrawl-playwright:20261107-lifecycle-v3`, but only one was the real `playwright-service-*` Coolify-managed API. **61** were abandoned QA runners (`/work/qa.js`, `/work/coverage.js`, `/tmp/qa.js`, `/usr/src/app/test.js`, `/tools/capture.js`, etc.) left running 19 minutes–three days by detached/timed-out browser tests. Prior load 8.51/10.59/9.98, RAM used ~25GiB, available ~5.8GiB, swap full at 8GiB. Each QA container was checked for age, exact MAD4B image tag, one-shot script, no restart policy, no published ports and non-managed status before a scoped `docker stop -t 2`. No Docker prune, WordPress service restart or MariaDB modification occurred.

A separate **five orphaned `node /tmp/mad4b-fixed-mobile.js` / `node /tmp/mad4b-mobile-smoke.js` QA roots** were still running **93.5 hours inside the managed Playwright API container**, attached directly to `containerd-shim` (not children of `node dist/api.js`). Their 30 browser descendants consumed ~970MiB aggregate RSS and sampled 24.4% CPU. A one-time process-tree cleanup verified exact process identity/start ticks before SIGTERM, selected **35 QA processes**, terminated all without kill escalation, and checked the native API process, unchanged container PID and health afterwards.

**After repair:** service processes 491→67, its memory ~670MiB→78MiB, sampled service CPU ~27%→0%. Host available RAM ~20GiB, swap down to ~5.6GiB (not forced off), and one-minute load declined to 4.66 at 23:11 UTC. Wayfatours home returned HTTP 200 / 17ms TTFB; Tours.dev home HTTP 200 / 3.67s TTFB. Readouts are single operational samples; CPU can still vary due WP-CLI jobs and uncached staging page renders.

## Permanent native prevention

Installed one root-owned owner under `/opt/mad4b-company-provisioning/operations/stale-playwright-qa-janitor-v1.py`, represented in this repository as `ops/company-code-release-v1/tools/stale-playwright-qa-janitor-v1.py`. The cron at minute 6/16/26/36/46/56 is `nice+ionice`, 100-second timed, lock-guarded. It first discovers exact MAD4B QA image-tag containers, protects Coolify-managed and restartable service processes, and stops only confirmed one-shot QA older than 45 minutes. It then discovers the actual API container by Coolify+Compose **semantic labels** rather than a fixed UUID, inspects its `docker top` tree, and reclaims only disconnected `/tmp/mad4b-*` test processes older than 90 minutes whose parent is the managed service's host containerd shim. It excludes API descendants, checks process start ticks against PID reuse and preserves API health.

The cron never changes media, booking, Elementor, cache settings, page CSS or JS. It stops orphaned QA only, never removes containers or volumes. Root crontab backup is at `/opt/mad4b-company-provisioning/backups/vps-cpu-qa-janitor-20261115/root-crontab-before-qa-janitor.txt`. To roll back, remove only the `MAD4B_STALE_PLAYWRIGHT_QA_JANITOR_V1` cron entry, preserve all other lines, and disable the script only under its exact hash. Do not restore the entire crontab over newer jobs.

**Verification:** hermetic safety tests `python3 ops/company-code-release-v1/tests/test_stale_playwright_qa_janitor_v1.py` (17/17) and live `--dry-run` with 0 candidate processes / production API retained. The live cron was observed as installed and the service remained healthy. Evidence receipts and preimage inventories are retained under `/opt/mad4b-company-provisioning/reports/vps-cpu-remediation-20261115/`.

Do not bypass commerce or release governance.
