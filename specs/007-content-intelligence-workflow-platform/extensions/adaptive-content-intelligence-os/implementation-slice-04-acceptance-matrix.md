## Follow-on source slice — Exact-scope Content Recipe resolution (P0-B)

Source path: `MAD4B_SCP_Content_Experience_Profiles` persists bounded `aci01_recipe_variants` inside its existing governed, revisioned `profile-plan` / `profile-apply` path, rather than creating a new option, schema, direct write route or parallel authority registry.

Each variant explicitly declares `site_uuid`, `brand_id`, `locale`, `market`, and 1–40 typed requirement identifiers. There is **no default**, wildcard, cross-site, cross-brand, cross-market or fallback locale. A profile supports at most 24 variants; duplicate scopes, duplicate requirements, malformed facts and foreign site IDs are rejected by the existing profile planning operation.

**Critical governance guard:** `MAD4B_SCP_Content_Experience_Governance::authority_payload()` now includes the optional `aci01_recipe_variants` in the existing profile authority digest and descriptor generation. Historical profiles without the key retain their historical hash until explicitly revised. Tampering with stored variant requirements without corresponding authority revision causes the existing `current_guard` to fail. The `ACI01_Recipe_Gap::resolve_current()` reader additionally checks profile authority, revision, post type, canonical site and exact per-market dimensions and rechecks profile status to deny a changing snapshot.

The Opportunity candidate uses `resolve_current` rather than passing a permanent `null` recipe to `evaluate`. An exact-scoped declaration contributes specific missing fact keys; missing configuration still presents `reviewed_domain_recipe` without inventing a generic recipe; invalid authority denies the candidate. The existing `mad4b/blueprint-build` handoff is unchanged and **never auto-dispatched**.

**Limits:** a governed profile declaration is **not** a standalone editorial acceptance, rights license, verified field owner, independent source receipt, AI quality certificate, or write grant. `Recipe_Gap::evaluate` continues returning `NEEDS_EVIDENCE` and `source_receipts_independently_certified=false`. Runtime and release gates must still enforce live approval, fresh scope and downstream factual attestations. No site-specific recipe rows are seeded automatically.

**Adversarial PHP fixtures added, execution NOT_RUN until an exact-source PHP environment is available:** brand/locale/market mismatch, duplicate scoped variant, duplicate fact, unknown key, oversized variant registry and requirement list, foreign site, wildcard language, stale profile revision, revoked authority and changed profile status during resolution. Legacy authority hash compatibility and stored recipe tamper rejection are separately covered. Source presence and hypothetical fixture expectations must not be reported as executed PHP PASS.


## P0 continuation — Pure candidate compiler and runtime generation fence

## Cross-feature Staging integration — dynamically complete, non-authorizing remediation loop

The existing `mad4b/staging-convergence-plan` now routes every blocked gate in the authoritative Staging certification snapshot to a bounded operator/remediation action. Existing governed routes retain their owners and exact approval controls; an unknown/new gate receives a **read-only** `review_gate_*` fallback derived from the gate's live evidence source and remediation owner, never an invented executor. The output includes `gate_action_coverage`, `plan_integrity_blockers`, `blocked_gate_count`, `covered_gate_count`, and `gate_coverage_complete`. This means *every gate has a diagnosis path*, **not** that each gate has an automatically available repair.

A missing prerequisite for `external_snapshot_refresh` now inserts the required authenticated MCP handshake readback even when `safe_boot` itself is currently passing. The reducer topologically sorts action IDs, refuses unknown dependencies/cycles/duplicates/malformed gate identities and oversized gate/action registries, and never silently lifts prerequisite constraints. No `governed_mutation`, external OAuth, hybrid creation or external browser job can inherit `automatic_execution_allowed=true`. Browser execution requires an independently verified identity, exact current-build plan, signed replay-safe receipt and fresh post-execution readback.

The optional `include_live_acceptance=true` overlays the **independent** `mad4b/live-acceptance-status` gate inventory onto the Staging planner with namespaced gate IDs. This opt-in costs more read work and is not enabled for routine cheap diagnostics; external WPML, live handshake/tools-list, production-unchanged, mutation/undo and request-surface evidence stay separate from local WordPress tests. Missing/unbounded/invalid external gate snapshots fail closed.

`mad4b/staging-convergence-verify` rereads the exact plan after each separately authorized repair. Its caller must supply the original `expected_plan_sha256` and `expected_source_commit_sha`. Any build or plan drift results in `REPLAN_REQUIRED`; missing authority yields `NEEDS_EVIDENCE`. Even a positive Staging-gate observation sets `full_release_certified=false`, `authorizing=false` and `mutation_performed=false`. The executor, approval ticket, external provider and release authority remain separate.

The no-WordPress PHP fixture `staging-convergence-coverage-runtime.php` exercises 40+ adversarial assertions for gate coverage, unknown site/provider gate safety, ordering, snapshots, source drift, cyclic/dangling dependencies, malformed gate identities, browser preflight, and release non-authority. It is registered in the existing offline Feature 007 preflight. **Exact native PHP execution, Staging re-upload and independent Browser/Host/Rollback certificates remain NOT_RUN/EXTERNAL_PENDING until verified**, regardless of fixture presence.


## Adversarial integration hardening — per-site identity, privacy, TOCTOU and provider registry

A build/source SHA does **not** uniquely identify a WordPress installation. The Staging Convergence planner now observes `MAD4B_SCP_Site_Profile::site_uuid()`, `profile_digest()`, origin, effective environment, native nonproduction-enrollment and URL parity before returning any successful Staging gate result. These fields enter the canonical plan binding and SHA, and the verifier explicitly refuses an empty/invalid site UUID, missing/invalid profile revision digest, Production environment or absent nonproduction admission. The planner retains the separate host/environment recovery options already present in Feature 007; it does not make a Production host appear Staging to bypass controls.

**Read generation fence:** the source manifest is SHA-256 hashed directly before and after the full Staging + optional Live acceptance read, intentionally bypassing the request-local provenance JSON cache. The new `runtime_identity_changed_during_plan` blocker also checks fresh Site Profile identity, source commit SHA, build fingerprint and package digest. This does not replace full file-integrity checks, transaction leases or cross-request CAS; downstream executors must still revalidate exact authority before effects.

**All actions are planning-only.** Every declared action receives `automatic_execution_allowed=false`, including provider-defined/unknown kinds, read-only hints and custom operation names. WordPress Ability registration is inspected separately; an absent `apply_ability` or `readback_ability` becomes explicit missing-provider metadata, **never** permission to install or run a host executor. Generated `review_gate_*` identifiers cannot silently replace provider-defined actions; collisions, dangling/cyclic dependencies and expanded-registry overflow invalidate the plan. Source text must not be used as permission evidence.

**Brand privacy:** central Staging plans always call Brand Context convergence with `include_authoritative_content=false` and `include_rendered_frontend=false`; authorized access to Brand Core source bodies belongs in its dedicated governed Context Ability, not an aggregated diagnostic response. This reduces accidental sensitive-context disclosure and volatile plan fingerprints.

The PHP fixture now includes **56 authored assertions**, including adversarial cross-site/Production/revoked-enrollment replays, stale profile identity, unsigned executor, action collision, no-auto for unknown provider kinds, true/false native Site Profile admission, and an isolated temporary-manifest change within one PHP process. Source shape/balanced-delimiter checks are **not a native PHP PASS receipt**. Run the fixture under PHP 7.4 and 8.3 plus disposable WordPress/DB and external Host/Browser assertions before claiming the mechanism is operationally certified.

**Residual accepted boundaries:** no automatic certificate minting, no production mutation, no source-rights self-approval, no guarantee that absent Hostinger/browser/WPML services become installed; no full-release claim from a Staging-only green check. The `mad4b/staging-convergence-verify` verdict is read-only and is re-created after separately authorized repairs.


## Staging Host Deployment Proof and Developer Isolation (post-upload live inspection)

A live governed read on All Royal Egypt Staging showed `Site_Profile.authority_ready=true`, `deployment_binding_configured=false`, `deployment_binding_bound=false`, and `same_origin_clone_protection=false`. The runtime correctly permits governed READ/WRITE, but local enrollment does **not** prove that this staging runtime is independently bound to its current Host. Previously, `deployment_identity_review` was advisory and could coexist with a green convergence summary once unrelated gates were clear.

The planner now adds the independent `deployment_host_binding` gate requiring configured, bound, matching deployment identity and same-origin clone protection, even if stored Site Profile enrollment itself is ready. A missing or mismatched host proof is linked to the existing `deployment_identity_review` action with a dedicated `mad4b/site-profile-status` readback, **never** a speculative host credential or mutation. This gate belongs to **release acceptance**, not the currently usable governed-write authority lane. The Site Profile must not be changed solely to simulate a passing host check.

The live `full-staging-authority-handshake` also reported `write_ready=true` but `operational_ready=false` because Normal Developer lacks resource limiting and network isolation. When Developer is requested, the planner now adds a separate `developer_host_execution` gate, mapped to the existing `developer_host_isolation_preflight` action and `mad4b/full-staging-authority-status` readback, which is verified READ-lane (unlike the Developer-only status Ability). An explicit blocker overrides any contradictory `normal_no_network_execution_ready=true` summary. No Breakglass, raw SQL or developer-host execution is authorized by this change.

The disposable PHP fixture adds adversarial conditions for missing host proof, same-origin cloned instance, mismatch after enrollment, ready-but-blocked host isolation, missing Developer host and correct gate-to-action coverage. The source-only PHP/contract checks require exact native execution before marking any related Spec task DONE.
