# Plan and controlled composition
1. Normalize all installed plugins and WordPress abilities into read-only source identities through already governed inventory, without executing plugins.
2. Collect `functional_coverage_report` and `Browser_Acceptance_Core::capabilities` into independent capability atlas groups.
3. Keep each Provider as a candidate, not an implicit preferred executor. Ambiguity is surfaced at capability level.
4. For capabilities covered by approved deterministic read-only vocabulary, a *native* WordPress Provider may compile its signed plan using server-side semantics and site/build identity.
5. The reviewed external driver only observes a whitelisted primitive. No arbitrary JS, CSS, POST, payment, WordPress changes, external URL or plugin install.
6. Validate case identity, nonce, origin, exact path, matched build and evidence envelope for every browser session.
7. Let the native independent reducer issue bounded PASS/FAIL/BLOCKED per capability. Never map atlas existence or a client-side `matches_expected` to a certificate.
8. For unsupported capabilities, create a read-only gap classification to route through existing Solution Discovery and Assistant Router. A candidate cannot authorize itself.
9. Perform exact-head native PHP and Node regression, staged browser trials for at least two dissimilar WordPress implementations, network provider controls, negative sabotage and package readback.
10. Only then consider governance-controlled release. Keep PR #258 Draft and master untouched.

### Lifecycle states
UNOBSERVED → INVENTORIED → DECLARED → SEMANTIC_ORACLE_READY → PRIMITIVE_APPROVED → PROBE_OBSERVED → NATIVE_REDUCER_VERIFIED → CAPABILITY_CERTIFIED.
Any missing gate → INCOMPLETE/BLOCKED. A capability family may contain many Providers and multiple independent proof methods.
