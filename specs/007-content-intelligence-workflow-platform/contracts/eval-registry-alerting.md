# Contract — Evaluation Registry, SLO Error Budgets and Alerting

Contract: mad4b.eval-operations.v1

## Eval registry

An EvalSuite has:
- suite_id/version;
- owner;
- domain/content type;
- language/market;
- fixtures/gold data refs;
- fixture provenance;
- scoring method;
- hard failures;
- thresholds;
- reviewer calibration;
- contamination policy;
- model/process applicability.

## Gold data governance

Gold fixtures:
- are versioned;
- have ownership/review;
- are not silently generated by the same candidate under evaluation;
- record source rights/classification;
- may include adversarial injection/security cases.

## Human agreement

Where human judgment is required, calibration MAY track inter-reviewer agreement and unresolved ambiguity.
Threshold changes are versioned and justified.

## Eval run

Records:
- candidate model/prompt/Skill/provider;
- exact input fixture set;
- scores/findings;
- hard blockers;
- baseline comparison;
- variance;
- evaluator version;
- result SHA.

## SLO and error budget

For each SLO profile define:
- objective;
- window;
- allowed error budget;
- burn-rate thresholds;
- alert severity.

Examples:
- provider execution success;
- queue age;
- publication verification;
- authority availability;
- job completion;
- callback latency.

## Alerting

Alert routes include:
- signal;
- threshold/burn condition;
- owner/on-call role;
- severity;
- dedup/group key;
- runbook;
- suppression/maintenance policy;
- escalation.

## Maintenance windows

Planned maintenance is explicit and does not erase raw metrics.
Security/authority incidents are not suppressed merely because maintenance is active.

## Post-incident learning

Incident outcomes feed:
- permanent tests;
- alert tuning;
- runbooks;
- provider certification probes;
- SLO changes where justified.
